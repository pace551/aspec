The premise

Why this exists

Handing an AI agent a chunky, multi-day build works — until you inspect the result and ask: are secrets handled? Are the tests meaningful? Did it set a budget alarm before deploying to AWS? Does the public-facing page meet accessibility standards? Is the SQL parameterized or is it one f-string away from injection? Without explicit direction, the answers to all of these depend on what the model happened to think about that session.

The framework makes these concerns rules, not suggestions — and backs each one with a script that has an exit code. Here is the full surface it governs:

SecretsNever in git, logs, or LLM prompts. .env discipline, vault ladder, rotation playbook.
TestingTest-first for core logic and every bugfix. Coverage ratchet that only goes up.
SecuritySAST, supply-chain audit, input validation, auth/authz, web hardening, threat modeling.
InfrastructureTerraform/OpenTofu, containers, serverless, networking — all with cost alarms and least-privilege.
OperationsStructured logging, alerting, deploy pipelines, backups with tested restores, incident response.
ArchitectureAPI design, error handling, idempotency, config management, concurrency, modularity.
UX & accessibilityResponsive design, WCAG 2.2 AA, loading/empty/error states, forms, SEO, email deliverability.
Data governancePrivacy/PII inventory, forward-only migrations, retention lifecycle.
LLM concernsModel selection from live data, prompt versioning, evals before changes, prompt injection defense.
ProcessRepo bootstrap, conventional commits, code review ladder, dependency management, CI baselines.
LegalDependency license audit, commercial launch checklist (ToS, privacy policy, DMARC).
CostAWS budget alarm before first deploy. LLM spend caps. No silent NAT gateways or always-on RDS.

The design bet, in one line:

Deterministic scripts verify; the LLM complies. — the framework's operating principle

No gate is a vibe. Every requirement is either checked by a command, blocked by a hook, or recorded as an explicit yes/no attestation — so drift is always visible, never silent.

What it does

The lifecycle, end to end

Day to day, the whole framework is five slash commands. A governed task moves through them in order:

  1. 1
    /govern — classify & select

    Applies a first-match rubric to pick the project's tier (T1–T4), detects its stacks, and selects only the standards that apply. Writes the result into the project's GOVERNANCE.md manifest and briefs the session on the hard rules. Ambiguity costs exactly one question — never a silent guess.

  2. 2
    /bootstrap-repo — scaffold with the gates on

    Copies the stack scaffold, installs git hooks (pre-commit: secret scan + lint; pre-push: tests + coverage ratchet), composes tier-appropriate CI from fragments, seeds CLAUDE.md / GOVERNANCE.md / .env.example — then proves its own gates fire (a canary secret commit must be rejected) before handing the repo over.

  3. 3
    Build normally

    The relevant rules are in context; hooks block the worst mistakes at write and commit time. Nothing else about the workflow changes.

  4. 4
    /verify-compliance — the "done" gate

    Executes every pinned standard's verification commands and prints a pass/fail table. Work is not done while this fails. Advisory rules become an attestation checklist — answered honestly and written into the manifest. A full pass stamps last_verified.

  5. 5
    /harvest-learnings → /evolve-standards — close the loop

    Friction (a rule that was missing, wrong, or too heavy) is captured as a structured note in the Obsidian vault. On a quarterly cadence — monthly for fast-churn areas like AI models — those candidates become human-approved, version-bumped diffs to the standards themselves.

How it works

Architecture

Constitution constitution/CONSTITUTION.md

Ten invariants loaded for every task at every tier: secrets never touch git · done means verified · test-first for core logic and bugfixes · spend requires consent · deviations are visible. Two pages, always in context.

▼  every task starts here
Tier rubric tiers.md

First-match classifier: payments/PII → T4 · deployed or other users → T3 · output-is-analysis → T2 · else T1.

Machine index index.json

Generated catalog of all 67 standards' frontmatter. Never hand-edited; never loaded wholesale.

Selector select-standards.py

Filters the index on tier + stacks + trigger keywords. Two modes: pins (everything applicable) and brief (what loads into context, ≤ ~15k tokens).

▼  selection writes the per-project contract
Project manifest GOVERNANCE.md

Tier · pinned standard versions · waivers (rule-scoped, expiry mandatory) · external-action approvals · PII inventory · attestations · last_verified. Pins make standards evolution non-breaking: the corpus moves forward, projects upgrade deliberately.

▼  the manifest is what gets enforced
Standards corpus standards/ · 11 families

SEC · TST · ARC · STK · INF · OPS · DEV · UX · DATA · AI · LEG. 403 rules with permanent IDs, per-tier applicability, runnable verification, worked examples, anti-patterns.

Verifier run-verification.py

Reads the manifest, runs every pinned standard's commands for the tier, honors waivers, fails expired ones, emits the attestation checklist. Exit code is the verdict.

Scaffolds & CI templates/

12 stack scaffolds + CI fragments (lint, test, ratchet, gitleaks, SAST, SCA, IaC scan, axe, Lighthouse, license audit) composed per tier by /bootstrap-repo.

Everything above lives in one dedicated git repo; projects carry only their GOVERNANCE.md.

The load-bearing trick: selective loading

Sixty-seven standards ≈ 14k lines — no agent can carry that. So context scope and enforcement scope are deliberately different. In context: the constitution plus rule-level detail for only the stack- and trigger-matched standards (measured worst case ≈ 10.8k tokens for a T4 full-stack product). Enforced: everything pinned, whether or not the session ever read it. You cannot dodge a rule by not loading it.

Proportionality

Four tiers, one rubric

Governance weight scales with blast radius — by rubric, not by mood. T1 stays light by design; a personal script that gains a public URL is a re-classification event, not a judgment call.

TierDefinitionPosture
T1 personalOnly you run it; breakage costs minutes Constitution + secrets + git hygiene hard; the rest advisory. Git hooks, no CI.
T2 researchOutputs inform real decisions; a wrong conclusion is the failure mode + test-first analytical core, provenance/leakage guards, reproducibility (pinned deps, seeds).
T3 productInternet-exposed and/or has users beyond yourself Full security/ops/UX required; CI mandatory; staging; accessibility + performance gates.
T4 commercialMoney, third-party PII, or public launch + legal baseline, retention/deletion, tested restores, license audit, MFA, DMARC.

The unit of the system

Anatomy of a standard

Each standard is one markdown file whose frontmatter is the API — machines act on it, humans read the prose below it. Rule IDs are permanent; waivers and attestations reference them forever.

---
id: SEC-SECRETS            # stable forever
version: 1.0.1             # semver; the index generator REFUSES unbumped edits
tiers: {T1: required, T2: required, T3: required, T4: required}
stacks: all                # or [python, nextjs, …] — drives selection
triggers: [secret, credential, api key, .env, …]
verification:              # executed by /verify-compliance; exit 0 = pass
  - cmd: "bash …/checks/secret-scan.sh"
    layer: G
    rules: [SEC-SECRETS-01]
  - cmd: "attest: any exposed secret has been rotated"
    layer: A
    rules: [SEC-SECRETS-05]
---
## Abstract → Normative Rules (RFC-2119, e.g. SEC-SECRETS-01)
## Verification → Worked Example → Anti-Patterns → Changelog

A framework linter (lint-framework.py) holds all 67 files to this schema — every rule required at any tier must be backed by a hard/gate check or an explicit attestation marker. The linter itself is mutation-tested, because a green linter you've never seen fail proves nothing.

Teeth

Three enforcement layers

Every rule declares how it's backed. Nothing is advisory-and-invisible.

H  Hard hooks

Block the action itself. A global Claude Code hook rejects any file write containing a live-secret pattern; per-repo git hooks reject secret commits and failing pushes.

G  Gates

Block "done." CI jobs and /verify-compliance commands — lint, tests, coverage ratchet (never decreases), gitleaks, SAST, SCA, IaC scan, axe, Lighthouse.

A  Attestations

Record drift. Advisory rules force an explicit followed: true/false entry in the manifest. Saying no is allowed; saying nothing is not.

Escapes are designed, not denied: disagree with a required rule and you grant a waiver — one rule ID, one reason, mandatory expiry (≤ 180 days). Expired waivers flip the gate to FAIL; a fixed violation flips its row to PASS. A rule that keeps collecting waivers is treated as evidence the rule is wrong — which feeds the evolution loop instead of piling up exemptions.

In practice

Using the framework — concrete scenarios

The lifecycle section above shows the flow. This section shows what it actually looks and feels like to use, across different project types and situations.

Scenario 1 — new project, full flow

Building a Python CLI that talks to the Anthropic API

You ask Claude Code to build a tool. The global CLAUDE.md triggers /govern automatically at the start of the task.

Governance intake: /govern
  Tier: T1 (personal — only you run it; first-match rubric line 4)
  Stacks: python
  Standards pinned (6): SEC-SECRETS 1.0.1, STK-PY 1.0.1, TST-POLICY 1.0.0, ...
  Hard rules for this task:
    SEC-SECRETS-01  No secret ever written to a tracked file
    SEC-SECRETS-02  .env (gitignored) + .env.example shipped
    STK-PY-03       ruff must pass (house config)
    STK-PY-04       bandit must pass
  Done = /verify-compliance green (Constitution C2).

The agent scaffolds via /bootstrap-repo: you get a src/ layout, pyproject.toml with the house ruff config, git hooks that scan for secrets on every commit, .env.example with placeholder keys, and a seeded GOVERNANCE.md. Then it builds your tool.

When the agent thinks it's done, it runs /verify-compliance:

verify-compliance · tier T1 · PASS
  [  PASS] STK-PY-03  ruff check .
  [  PASS] STK-PY-03  ruff format --check .
  [  PASS] STK-PY-04  bandit -r src -q
  [  PASS] STK-PY-02  pytest -q
  [  PASS] SEC-SECRETS-01  secret-scan.sh
  [  PASS] SEC-SECRETS-02  .env not tracked, .env.example exists
  last_verified: 2026-09-15
What you got that you wouldn't have without the framework: secrets discipline enforced by hook, not hope. Lint and security scan baked into the commit cycle. A machine-verifiable definition of "done" instead of "I think it's ready."

Scenario 2 — the gate catches a real problem

Agent builds a FastAPI service with a database query

The agent writes f"SELECT * FROM users WHERE id = {user_id}" — an f-string SQL injection, the canonical anti-pattern the framework was designed to catch.

verify-compliance · tier T3 · FAIL (1)
  [  PASS] STK-PY-03  ruff check .
  [  FAIL] STK-PY-04  bandit -r src -q
           | Issue: [B608] Possible SQL injection via string-based query
           | Severity: Medium   Confidence: Low
           | CWE: CWE-89
           | Location: src/app/db.py:14

The agent cannot declare done. It fixes the query to use parameterized placeholders, re-runs the gate, and the row flips to PASS.

What happened: a deterministic scanner caught an injection vulnerability that the model introduced and would have shipped without the gate. The framework didn't rely on the model noticing its own mistake.

Scenario 3 — a personal tool goes public

Your T1 script now has a URL and other users

You re-run /govern. The rubric re-classifies: "deployed beyond localhost with internet reach" → T3. The standard set jumps from 6 to ~40. CI becomes mandatory. Security, accessibility, and performance gates activate. /bootstrap-repo can retrofit what's missing (CI workflows, healthcheck endpoint, content security policy headers).

The point: escalation is cheap and mechanical. The framework doesn't punish growth — it adjusts the safety net to match the new blast radius.

Scenario 4 — you disagree with a rule

pip-audit flags a CVE that isn't reachable in your code

The gate is failing on STK-PY-05 (dependency vulnerability audit) for a CVE in a transitive dependency you never call.

# You grant a waiver — one rule, one reason, mandatory expiry
waivers:
  - rule_id: STK-PY-05
    reason: "CVE-2026-12345 in lxml — we use none of its XML parsing;
             unreachable. Upgrading blocked on numpy compatibility."
    expires: 2026-12-01
    granted_by: you

The gate now shows WAIVED for that rule. If you don't fix it by December 1, the waiver expires and the gate fails again — renewal is a fresh, conscious decision.

Waivers are escapes, not loopholes. The rule that keeps getting waived feeds the evolution loop — it's evidence the rule itself may be miscalibrated, and /evolve-standards surfaces that pattern.

Scenario 5 — working on an existing governed project

Adding a feature to a repo that already has GOVERNANCE.md

When you open the session, the banner hook prints:

Governed project: tier T3 · last_verified 2026-08-22 · done = /verify-compliance green

/govern re-runs (cheap — one script call) to re-confirm the tier and flag any standard-version drift. You work normally. Before the PR, /verify-compliance runs the full check suite. The PR description carries the pass/fail table as evidence.

Scenario 6 — something felt wrong

A rule was too heavy for a T1 script, or a gap wasn't covered

After the task, run /harvest-learnings. It asks what was missing, wrong, or disproportionate, and writes a structured note to the Obsidian vault. On the next quarterly /evolve-standards pass, those notes become proposed diffs to the standards themselves — version-bumped, changelogged, and applied only with your approval.

The framework learns from use. Over-governing a personal script is treated as a bug, same as under-governing a public product.

Self-application

The framework governs itself

  • Versioned evolution: standards change only via /evolve-standards — human-approved diffs, semver bumps, changelogs. The index generator hashes every file and refuses to index a content change without a version bump.
  • Own CI: the repo runs its self-lint, script lint, shell syntax checks, and a full-history gitleaks scan on every push.
  • Negative fixture: a generator builds a deliberately broken project (hardcoded key, f-string SQL, coverage below baseline, expired waiver) and the test asserts the verifier fails it citing the exact rule IDs — then flips when one violation is fixed.
  • Verified examples: one small real project per stack, each run green through its own gates (Python, TypeScript, Go, Next.js, Vite+React, HTMX; Rust and SwiftUI written, pending local toolchains).

Getting started

Installation

Prerequisites

  • Claude Code — the framework is designed for Claude Code's skill and hook system
  • Python 3.11+ with PyYAML — powers the index, linter, selector, verifier, and coverage ratchet (pip install pyyaml if not already available)
  • gitleaks (recommended) — secret scanning at commit and CI time; the framework degrades to a built-in pattern scan without it, but gitleaks has broader coverage (brew install gitleaks on macOS)

Per-stack tooling (ruff, bandit, eslint, gosec, etc.) is installed per-project by /bootstrap-repo — you don't need all of them upfront.

Clone and install

# 1. Clone the repo (anywhere you like)
git clone https://github.com/you/aspec.git ~/aspec

# 2. Install the five skills into Claude Code
cd ~/aspec
bash checks/install.sh

# 3. Point Claude Code at the framework (writes ~/.claude/CLAUDE.md)
bash checks/install.sh --global-claude

# 4. Wire the global hooks (optional — adds the blocking pre-write
#    secret scan + session banner; makes a timestamped settings backup)
bash checks/install.sh --hooks

Each step is idempotent — re-run install.sh after pulling updates to refresh installed skills and hooks. The canonical sources stay in this repo; the installed copies are what Claude Code reads at runtime.

What each step does

StepWhat it installsWhere
install.sh Five skills: /govern, /verify-compliance, /bootstrap-repo, /harvest-learnings, /evolve-standards ~/.claude/skills/
--global-claude A small CLAUDE.md that tells Claude Code to run /govern before chunky tasks and /verify-compliance before declaring done — the always-on pointer that makes the framework apply everywhere ~/.claude/CLAUDE.md
--hooks A PreToolUse hook that blocks writes containing live-secret patterns (the only blocking hook — deliberately narrow), and a SessionStart hook that prints a one-line governance banner in repos with a GOVERNANCE.md ~/.claude/settings.json

Verify the installation

# The framework should lint itself clean
python3 checks/lint-framework.py
# → lint-framework: clean (67 standards)

# The selector should find standards
python3 checks/select-standards.py --tier T1 --stacks python \
  --brief-text "cli tool" --mode brief | head -5

# Start a new Claude Code session — you should see the five
# governance skills in your available slash commands

Uninstalling

The installer only writes to ~/.claude/ — it never modifies your projects. To remove:

# Remove skills
rm -rf ~/.claude/skills/{govern,bootstrap-repo,verify-compliance,harvest-learnings,evolve-standards}

# Remove global CLAUDE.md (or edit it to remove the governance block)
rm ~/.claude/CLAUDE.md

# Remove hooks — restore from the timestamped backup
cp ~/.claude/settings.json.bak.YYYYMMDDHHMMSS ~/.claude/settings.json
